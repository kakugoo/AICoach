# Architecture

The browser talks to FastAPI over HTTP. FastAPI owns business logic and database access; the browser never connects directly to PostgreSQL. PostgreSQL runs locally through Compose. Health and readiness are separate: `/health` checks the API process; `/ready` executes a database query and returns 503 if unavailable.

Later, a separate worker can claim durable database jobs and call an isolated parser adapter and versioned analysis module. Match facts, heuristic assessments, and future model interpretations must remain distinguishable. A repeated analysis creates a new versioned run; no FACEIT profile is required for manual demo analysis. These are design intentions, not implemented features.

This development setup binds the database to localhost. Example credentials are local-only. The upload and worker design below is for local use and needs hardening before public deployment.

## Accounts and sessions

Users have normalized unique email addresses and Argon2id password hashes. An opaque 256-bit random session token is held in an HttpOnly, SameSite=Strict cookie; only its SHA-256 digest is stored in PostgreSQL. Sessions expire after seven days; logout deletes the server-side row, and authentication replaces an existing session. Authentication and domain access are separate: `/auth/me` resolves the current user from the session, never from a client-supplied user ID.

Mutating auth endpoints require a configured exact Origin and a custom header; CORS allows credentials only for configured origins. Cookies use Secure and the `__Host-` prefix when `COOKIE_SECURE=true`; configure HTTPS and allowed origins explicitly before deployment. These protections apply to future mutating endpoints too. Local HTTP uses an unprefixed cookie.

A PostgreSQL-backed 15-minute rate limit is enforced independently per client IP and normalized email on login and registration; transaction locks coordinate workers. All attempts count, including successful ones (five per email, thirty per IP). This is deliberately conservative and can temporarily prevent legitimate access, especially on shared IPs. It is not a complete public anti-abuse solution: before deployment design trusted proxy/IP handling, distributed attack defenses, monitoring, retention and cleanup, session idle expiry, email verification, recovery, and deployment hardening. Client IP is taken from the direct connection, never from untrusted forwarding headers. Argon2 consumes CPU and memory, so capacity must be assessed under load.



## FACEIT profiles

The backend alone uses the FACEIT Data API server key as a Bearer token. `GET /players?nickname=...` performs exact nickname lookup, and `GET /players/{player_id}` obtains fresh data before adding or refreshing a profile. No unverified client-supplied profile fields are stored. External response errors and timeouts map to generic safe errors. Local rate limits share the existing PostgreSQL-backed mechanism, applied separately to IP and user for all external FACEIT operations. A missing key disables those operations, but not listing or removing previously tracked profiles. The status reports configuration only, not key validity.

`faceit_profiles` stores global player information, uniquely identified by FACEIT Player ID. `tracked_profiles` stores a unique user/profile pair and the addition time. Users may independently track the same profile. Deleting a tracking relationship never deletes the global record. Updates to a shared profile are visible to all trackers. Steam ID64 is stored only when FACEIT returns a valid 17-digit `steam_id_64`; it is a future matching hint, not proof of ownership or an implemented demo association. CS2 ELO and level come only from `games.cs2` and remain null when missing. A profile URL is built from the validated nickname rather than trusting arbitrary URLs returned by the API. Profile ownership is never asserted.

All endpoints require the existing user session; state-changing requests use the existing Origin and custom-header CSRF checks. FACEIT requests have a timeout and use a fixed host with redirects disabled. Data from the external service is not logged. Before public deployment, review quota, proxy/IP trust, retention and cleanup of orphaned profile records, and abuse protection; current limits are intentionally conservative.

## Demos and worker

The authenticated browser streams a raw `.dem` or `.dem.zst` request with declared Content-Length, origin and CSRF checks. API verifies extension and matching magic, reserves compressed or original bytes in PostgreSQL under a transaction lock and writes a randomly named temporary file. It checks quotas and disk space before recording the upload. A single worker claims jobs using row locks and holds a PostgreSQL advisory lock. For compressed input it reserves additional disk space against the global quota, runs bounded single-frame Zstandard decompression in a subprocess with a separate decompressed-size limit and timeout, validates end-of-frame and the CS2 signature, and always removes the temporary decompressed copy. Original uploads remain for repeat analysis. On restart stale work is requeued and reserved temporary space is reset. A crashed parent can leave an orphaned child temporarily; production deployment requires a supervisor or process isolation.

Result persistence is transactional: successful processing replaces one materialized match, its players and rounds and records parser/algorithm versions. A failed reprocess leaves the old rows untouched, though the interface hides them while the task is not completed. Each upload and result is accessible only to its owner. No nickname matching to FACEIT is performed.

## Competitive normalization (`competitive-2`)

The parser preserves every extracted death event and its tick in `facts.events`, alongside exclusion reason, participants and teamkill/suicide flags. Normalization requires a `begin_new_match` reset, a subsequent match-start announcement in game phase 2 at zero rounds, live freeze-end markers with consecutive round numbers and an end-of-match panel. Without these facts or with incomplete/restarted sequences the algorithm withholds competitive statistics. A preliminary knife round is identified only when a separately signalled phase-1 start is followed by a warmup announcement before the reset, with its events corroborating the classification. It is not inferred from a knife kill alone. Uncertain pre-match intervals remain unknown. Warmup flag, game phase, match-start state, round number and tick bounds are considered for each event; post-match and unknown phases are excluded. Individual exclusion reasons are retained. A finish marker is not itself proof that no earlier round-end timing ambiguity exists.

Stable groups are formed from player Steam IDs and sides at the first live freeze end, then checked against player-side and `team_rounds_total` snapshots at each subsequent freeze end and at match completion. Only when score changes are consistent and each completed round has exactly one point does the service emit a score, winner and round-side mapping; side switches are recorded. Team names are labels, not ownership verification. Substitutions, unusual phase numbers, overtime and incomplete demos need further real-data verification; unknown/ambiguous phase or identity data suppresses totals instead of guessing. The sampled side switch time is a freeze-end observation, not necessarily the exact switch instant.

K is enemy kills excluding teamkills and suicides; D includes player deaths including teamkills and suicides; A counts a distinct assister on the attacker's side; headshots count eligible enemy kills marked headshot. Unknown assistant teams or headshot flags suppress the corresponding metric. K/D is shown only if D > 0. Events outside eligible rounds do not affect these counts. A real FACEIT demo matched supplied K/D/A references for a subset of players after pre-match and post-match events were excluded; remaining results have not been independently compared with FACEIT. Do not treat this single example as proof of universal FACEIT equivalence.

## Advanced player analytics (`advanced-1`)

`competitive-2` remains the unchanged source for competitive round boundaries, teams, score and its existing K/D/A. The separately versioned `advanced-1` result is stored in the match `facts` JSON and replaced in the same transaction on retry, so no schema migration is required. Old results have no advanced data until reprocessed. `advanced_source` records selected original damage and disconnect fields; `events` retains the original normalized death evidence. Advanced per-round data and aggregate data are distinct from both sources. No result is shared between owners.

A participant is confirmed only when a Steam ID has a freeze-end snapshot alive at 100 health, with a known CT/T side consistent with the roster. An absent or inconsistent snapshot is unknown rather than a confirmed absence. Each round also requires exactly one `round_end` event within the previously verified interval whose winner matches the previously determined side. Only events up to and including that marker feed advanced metrics. End-of-round survival requires an alive snapshot at that marker; an unexplained missing snapshot is unknown. A disconnect between the start and end makes survival unknown unless a death is known, and makes that player's damage unknown. If any round's participation is unknown, match-level metrics requiring a denominator are withheld; this conservative first version does not estimate partial participation.

Damage is health lost to opponents: `previous integer health - health after hit`, capped by previous health. The parser's reported integer damage must agree within one point (to allow integer rounding); otherwise damage for that round is unknown. Team damage, self-damage and armour damage are excluded from the attacker's total, while all damage to a victim updates health. ADR is total valid enemy health damage divided by confirmed played rounds, withheld if any round's damage or participation is uncertain. This is not independently validated as FACEIT's formula.

K/D is kills divided by deaths when deaths > 0; K/D difference is kills minus deaths; headshot percentage is 100 times headshot kills divided by kills; kills per round is kills divided by confirmed rounds. KAST is 100 times the fraction of confirmed rounds with an enemy kill, eligible assist, verified survival, or death traded. A round is counted at most once; any unknown KAST round suppresses the aggregate. An opening duel is the first eligible enemy death in a verified round; equal-tick first kills or unresolved earlier deaths make it unknown. Win percentage is 100 × opening kills / opening participations; participation percentage is 100 × (opening kills + opening deaths) / confirmed played rounds.

A trade is an enemy kill by a teammate of a victim against that victim's killer, strictly later in the same round and within `DEMO_TRADE_WINDOW_TICKS` (default 320). Same-tick order is not inferred. This is an event-based heuristic; it does not prove player intention and 320 ticks represents five seconds only when the recording uses 64 ticks per second. Time conversion is not inferred from the demo. CT/T aggregates use the verified side at each freeze end, including side changes. K/D/A in advanced rounds stop at `round_end`; historical `competitive-2` values remain unchanged even where its boundary rules differ.

The engine currently requires a full roster and has not been independently validated against FACEIT ADR, KAST, trade definitions or multiple demos. Overtime, substitutions, ambiguous identities, unusual phase behavior and disconnected players need further real-match verification; no tactical error or recommendation is inferred.

## Overview and analytics UI

`GET /demos/summary` authenticates the current user, joins only that user's uploads with their match records, and returns counts and the latest five records. It does not expose a saved analysis while its job is incomplete. The overview refreshes periodically and re-fetches after returning from the match list; no additional database table or migration is required. The player dashboard reads the existing owner-protected detail API once and switches tabs locally.

A `.zst` filename is accepted alongside `.dem.zst`: the API still requires the Zstandard magic and stores a random internal `.dem.zst` filename. The worker retains bounded, single-frame decompression, verifies the CS2 demo signature and deletes temporary copies. A valid Zstandard header alone does not prove the archive contains a valid CS2 demo; that is checked asynchronously by the worker.

## Primary profile and personalized scores

`tracked_profiles.is_primary` is scoped to a user; a partial unique index permits at most one primary profile per user. Selection locks the user row and requires an existing tracking relation, with the usual session and CSRF checks. Removing that relation clears the selection naturally without deleting the global FACEIT profile. A primary profile is a display preference and does not establish ownership; no external API key is needed to select it.

For each completed `competitive-2` result, the backend compares the stored Steam ID64 exactly against match participants and accepts exactly one match. The player's stable team label is matched against exactly one of the two validated score entries. When all evidence is present, the player's team is placed first and the outcome follows the scores. Missing IDs, duplicate participants or ambiguous team labels suppress personalization; CT/T side switches do not affect the team mapping. Match summaries and detail responses calculate this dynamically, so changing the preference needs no reprocessing of demos.

## Local profile as a personalization source

`local_game_profiles` stores at most one local Steam ID64 and its demo-derived display nickname for each user. Selection accepts an owned completed demo ID and its player ID, resolves and validates the identifier on the server, and rejects missing or duplicated IDs. It does not accept a client-supplied Steam ID as evidence, infer identity from nicknames, or prove account ownership. The selected ID survives deletion or reprocessing of the originating demo.

There is one active personalization source at a time. Choosing a local profile clears the user's `tracked_profiles.is_primary`; choosing a tracked FACEIT profile deactivates the local record but preserves it. Both transitions lock the user row and commit atomically. Removing the local record does not delete tracked FACEIT profiles, and no automatic fallback silently activates another source. Existing FACEIT selections remain active through the migration. The shared score and player matching path resolves the active Steam ID64 before performing the existing exact, unambiguous match; no competitive or advanced analysis methods are changed. This leaves room for future explicit cross-source identity confirmation.

## Utility and economy (`utility-economy-1`)

A separate versioned result is materialized in the existing match facts transaction, leaving `competitive-2` and `advanced-1` untouched. It uses only rounds with `advanced-1`-verified end ticks and confirmed participants. `weapon_fire` with the specific grenade weapon names counts uses; `player_blind` counts individual blind events by attacker and relation, including self separately. Event duration is retained when finite. No tactical effectiveness, unique-flash metric or flash-assist is inferred. Smoke detonation and expiry events are retained separately with ticks and entity IDs in owner-only diagnostics, including pre-match events; they are not counted as throws. Normalized use, blind and hurt events retain ticks and participant IDs for later examination. Large event lists are omitted from ordinary match detail responses and input event counts are capped at 200,000 after parser extraction; the parser itself can still consume significant memory on large demos.

For each participating player, health starts at 100 at verified freeze end. All `player_hurt` events until the verified round-end update victim health. Effective grenade damage is previous health minus remaining health; the parser's damage must agree within one integer point, accounting for overkill and rounding. Damage is grouped as HE or `inferno` (fire cannot reliably be split into Molotov and Incendiary), and by enemy, ally and self. Same-tick damage to the same victim, unknown identities, inconsistent health or disconnection suppress affected round totals; a missing round suppresses match totals. These values do not change ADR. The stream may be incomplete in unusual demos, so this is not independently verified as FACEIT's method.

Economy samples `balance`, `current_equip_value`, `cash_spent_this_round`, `armor_value`, `has_helmet`, `has_defuser` and `inventory` at round freeze end. Balance is current cash, equipment value is current loadout value, and cash spent is the game property, not a reconstructed purchase ledger. The team sum is emitted only when all known roster members have confirmed snapshots and equipment values. Snapshots do not determine cash before buying, saved equipment, purchase history or buy classifications; none are invented. Inventory is reported as observed, without guessing primary weapon. Old results must be reprocessed to populate the new version. Extraction failure produces an unavailable utility/economy result rather than breaking old analytics; it does not prove an event count is zero.
